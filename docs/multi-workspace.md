# Multi-workspace (design)

**Status: design, built in phases; phase 2's data path is complete since 7.14.00.** This document describes how one deployment of the platform will serve
several separate teams or customers, each in its own **workspace**. Only what the table below lists exists in the code;
everything else is planned, and each release's CHANGELOG entry says what landed and updates the table. Routes, tables
and files named here are the planned ones unless the table lists them.

| 6.09.00 | Creating and listing workspaces, for platform admins only, in the workspaces API under `/platform/{proxy+}` (GET and POST, Cognito; logic in `lambda/shared/platform_workspaces.py`). It answers 201 `{workspace: {id, name, slug, role: 'admin', secret_status}}`. The transaction's idempotency token covers the SDK's own retries; a client that retries after a lost answer gets 409 for the slug its first attempt took, and `GET /platform/workspaces` shows whether that workspace was made. Then it creates the workspace's credentials secret (Credentials, below); `secret_status` is `ready`, or `pending` when the secret could not be made (logged; the workspace stays). `GET /platform/workspaces` lists every workspace `{workspaces: [{id, name, slug, status, created_at, secret_status}], next_cursor}` by name (`?limit=` 1 to 100, default 25, `?cursor=`), one Query of the `WORKSPACES` partition. The role's PutItem reaches `AUDIT#WS#*`, `SLUG#*`, `USER#*`, `WORKSPACES` and `WS#*`, its UpdateItem `WS#*` and `WORKSPACES` only (`secret_status` on `META` and the listing row, in one transaction); it reads the caller's groups and account in Cognito, and creates, describes and tags secrets under `voc/ws/*` only. | 6.10.00 | A workspace's members, in the workspaces API under `/me/workspaces/current/members` (GET, POST, PUT and DELETE on the existing `/me/{proxy+}`; logic in `lambda/shared/workspace_members.py`), each acting in the workspace `X-Workspace-Id` names as `resolve_workspace` decides (400 without the header, the one 404 for a non-member, the deployment's `admins` group included; a platform admin enters as admin, live-checked and audited). `GET` lists the members `{members: [{sub, role, email, name, invited_by, joined_at}], next_cursor}` for any member, by sub (`?limit=` 1 to 100, default 25, `?cursor=`; one Query of the `MEMBER#` rows; email and name are the row's, and for up to 5 rows a page that hold none, such as the creator's, Cognito's by sub). `POST {email, role}` (admin, editor or viewer): workspace admins only (`require_workspace_admin`: 403 for an editor or a viewer); an email with a Cognito account is a member at once, a new email first gets an account (`AdminCreateUser`, the temporary password emailed, as the users API does) when the caller is in the deployment's `admins` group (platform admins are; 403 for any other workspace admin: until the data path is keyed by workspace, phase 2, every account reads the whole deployment, so creating one stays with the users API's administrators), then 201 `{member: {sub, role, email, name, invited_by, joined_at, account: 'existing'\|'created'}}`; 409 for a member already there, for two accounts sharing the email, or for an email Cognito holds for another account. An existing account gets no notification email: the deployment has no mail path for account notices, so the add is logged. No `INVITE#` row is written: membership is immediate either way, so there is nothing to accept. `PUT /{sub}` `{role}`: workspace admins only (asking for the role a member has changes and records nothing). `DELETE /{sub}`: workspace admins, or the member themselves (leave). Demoting or removing the last member admin, the caller included, is refused (409). Each add, role change and removal writes an `AUDIT#WS#{ws}` / `{iso}#{random}` row (kind `member_added`, `member_role_changed`, `member_removed` or `member_left`; actor, target sub, role before and after, `platform_admin`, and on an add `account`) before the change, so it records the attempt (a row that cannot be written refuses the change); then ONE transaction changes the `MEMBER#` row and the `USER#` row together (an add: two conditional puts and a check that `META` is still `active`; a role change: two updates, each only of `role` and only on existing rows; a removal: two deletes), and a demotion or removal of an admin also checks that another member is still an admin, so two admins demoting each other at once cannot both succeed. Each write resolves the caller's role from the table, not the 30 s cache, so an admin demoted or removed a moment ago cannot undo it; the change drops the member's cached membership in the container that made it, and other warm containers serve the old role to reads for up to 30 s. The role's new grants: UpdateItem on `WS#*` and `USER#*` with the attribute `role` only; DeleteItem on `WS#*` and `USER#*` (`dynamodb:LeadingKeys`; IAM cannot pin a sort key, so `META` in `WS#*` is in reach of IAM and kept out by the code, while `SLUG#`, `WORKSPACES` and `AUDIT#` are not); ConditionCheckItem on `WS#*`; Cognito `ListUsers` and `AdminCreateUser` on the user pool (IAM cannot limit ListUsers to an email filter; the code sends only an email or a sub). The web app calls these routes since 6.13.00 (the members page) |

## Upgrading

Multi-workspace starts on a fresh deployment (decision 12): an existing deployment does not take the release that
re-keys gsi4 and gsi5 (7.00.00, the processor's slice above) in place, and nothing is migrated.

- Why: `gsi4-by-feedback-id` and `gsi5-by-channel` move from the raw `feedback_id` and `source_channel` to
  `gsi4pk` and `gsi5pk`. Changing an index's key is a delete and a create, and DynamoDB allows one index change per
  table update, so CloudFormation refuses the update. And items stored before carry no `gsi4pk` / `gsi5pk`: they
  would be in neither index, so every lookup by id (`GET /feedback/{id}`, the feedback edits, the Data Explorer, the
  assistant) and every channel filter would miss them.
- An operator who must upgrade an existing deployment re-keys in steps, one deploy each: remove gsi4; add gsi4 on
  `gsi4pk`; remove gsi5; add gsi5 on `gsi5pk` (pinning `lib/stacks/core-stack.ts` to each intermediate shape), and
  backfills every `FEEDBACK#` item with `gsi4pk = FEEDBACK#{feedback_id}` and, where `source_channel` is not empty,
  `gsi5pk = CHANNEL#{source_channel}` (a paged Scan and conditional updates) before relying on either index. Until
  the backfill ends, reads by id and by channel miss the items not yet updated.
- Credentials (decision 19, since 7.12.00): a workspace's credentials live in SSM Parameter Store
  (`/voc/ws/{ws}/credentials/{plugin}`) and their config lists in voc-aggregates rows (`WS#{ws}#PLUGIN_CONFIG`), and nothing reads the Secrets Manager
  secrets `voc/ws/{ws}/credentials` that 6.09.00 created per workspace. They are not migrated: this release is for a
  fresh deployment (decision 21). An existing deployment that takes it anyway must save each workspace's
  credentials, app connectors and scrapers again in that workspace, then delete the old `voc/ws/*` secrets by hand
  (each still bills about $0.40 a month until deleted). The deployment's shared secret (`SECRETS_ARN`) is unchanged.
- Conversation owners (since 7.19.00): a workspace's list of conversation owners (`WS#{ws}#CONVERSANTS`) is written
  by every save from 7.19.00 on, so a fresh deployment (decision 21) needs nothing. A deployment that ran 7.15.00 to
  7.18.00 with workspaces in use runs the one-off backfill once after the deploy, from `voc-datalake/`:
  `.venv/bin/python scripts/conversations/backfill_conversants.py` (a dry run: it prints each owner it would list),
  then the same with `--apply`. It scans voc-conversations once for the `CONV#` rows of `WS#*#USER#*` partitions and
  puts each owner's row if absent (`first_at`: their earliest `created_at` there), through the chat routes' own
  writer, so it is safe to run again and keeps a row a save wrote meanwhile. The table: `--conversations-table`,
  else the `CONVERSATIONS_TABLE` environment, else the core stack's `ConversationsTableName` output (`--stack`,
  `--region`). It needs Scan, GetItem and PutItem on the table and the KMS key's use.

## Model

The pool model: one deployment, and every row and object carries its workspace.

- **Workspace id**: `ws_<ulid>`, plus a unique, immutable `slug` for URLs.
- **DynamoDB**: every partition key is prefixed `WS#{ws}#…` (for example `WS#{ws}#SOURCE#webscraper`), and so is
  every GSI partition key (`WS#{ws}#DATE#2026-01-15`). No GSI is ever queried without the prefix.
- **S3**: `ws/{ws}/raw/{source}/{yyyy}/{mm}/{dd}/…`, `ws/{ws}/avatars/…`, `ws/{ws}/exports/…`, and so on for every
  prefix described in [Data Lake Structure](data-lake-structure.md). The raw tier keeps its contract (write-once,
  `If-None-Match`, nothing expires) under each workspace's prefix.
- **KMS**: the one customer-managed key stays (tenet 7); where the platform encrypts data itself it passes
  `workspace_id` as encryption context.

## Request flow

1. A person signs in (one Cognito user pool) and the web app calls `GET /me/workspaces`. With exactly one workspace
   the picker is skipped; with none, it says so and names who can invite them. Since 6.12.00 (the table above) the
   picker and the one-workspace skip are built; a person with no workspace still gets the app as before workspaces,
   because the data path is not keyed by workspace yet. The "no workspace, ask who can invite you" screen comes with
   phase 2, when the data path requires a workspace.
2. The web app keeps the current workspace in the URL (`/w/{slug}/…`) and sends `X-Workspace-Id` on every API call.

## Invites

Built in 6.10.00 (`POST`, `PUT` and `DELETE /me/workspaces/current/members[/{sub}]`, `lambda/shared/workspace_members.py`).

- Workspace admins and platform admins invite, with any workspace role. Editors and viewers cannot (403).
- An email that already has an account gets its membership row at once. The notification email is not sent yet:
  the deployment has no mail path for account notices (the participant mailer serves participant asks only), so the
  add is logged and the answer says `account: 'existing'`.
- A new email gets a Cognito account (`AdminCreateUser`, which sends the temporary password) and the membership row
  at once (`account: 'created'`), when the caller is in the deployment's `admins` group (a platform admin is): any
  other workspace admin gets 403 for a new email until the data path is keyed by workspace (phase 2), because until
  then every account reads the whole deployment. The account joins no deployment group (neither `admins` nor `users`): inside a
  workspace only the `MEMBER#` role counts. The creation is recorded before the account exists: an `AUDIT#WS#{ws}`
  row of kind `account_created` (the actor and the email's sha256: no role can change or remove an audit row, so a
  raw address there could never be erased), written before `AdminCreateUser`, so a row that cannot be
  written creates no account. If the membership then fails (its audit row or its transaction), the account stays,
  recorded; adding the email again finds it.
- Membership is immediate in both cases, so no `INVITE#` row is written (Control plane).
- Removing or demoting a workspace's last admin is refused (409), the admin themselves included. Any member may leave
  (remove themselves). A person with no workspace left gets the app without a workspace (until phase 2, Request
  flow step 1).
- A change takes effect at once in the container that made it; other warm containers serve the member's cached
  role to reads for up to 30 s (`MembershipCache`, `lambda/shared/workspace.py`). The members writes never use the
  cache: they read the caller's role from the table, and each transaction also checks that the acting admin is still
  admin when it commits (403 when they were demoted in between).
- Trade-off, accepted with decision 4 (an invitee may already have an account): adding by email tells any workspace
  admin whether the email has an account in this deployment, and its name (201 for one with an account, 403 for a
  new email from an admin outside `admins`). It is one deployment's own directory, which only `admins` list in full
  (`GET /users`); a multi-company deployment would answer both cases alike.
- Deleting a user (`DELETE /users/{username}`, since 6.11.00) removes their memberships too, in this order: every
  refusal first (the users API's own: the caller's own account, the last administrator, a platform admin's rules;
  then the last member admin of any of their workspaces, 409, which names the workspace), then a platform admin's
  revoke audit row, then per workspace its `member_removed` audit row (`via: user_deleted`) and one transaction of
  the `MEMBER#` and `USER#` deletes, and only then the Cognito account (`AdminDeleteUser`). So a refusal, or a fault
  before the account goes, leaves the account as it was: a fault part-way leaves the memberships not yet removed (the
  ones removed stay removed, audited), and the delete can be asked again. A platform admin may delete a workspace's
  last admin: the workspace then has no member admin (the audit row says `left_without_admin`) until a platform admin
  enters it (decision 2) and makes a member admin, or adds one (`PUT` or `POST /me/workspaces/current/members`).
  Other warm containers serve the deleted user's cached membership to reads for up to 30 s.
- A member admin whose Cognito account is disabled still counts as an admin when another admin is demoted or
  removed: the check reads the table, not Cognito (one Cognito call per admin on every demotion and removal would be
  the alternative), and a disabled account may be enabled again. Their rows stay; deleting the account removes them.
  Known gap: a user deleted before 6.11.00 kept their rows, so they still count as another admin. To clean up, check
  each workspace's members against the users list and remove any member whose account is gone.
- Erasure (D5, since 6.11.00): an erasure by email without a source (`POST /settings/erasure`, `voc-retention`,
  docs/source-policies.md) removes the `email` and `name` of every `MEMBER#` row that holds that email (compared
  case-insensitively: a row keeps Cognito's spelling) and keeps the row, as the feedback boards keep a de-identified
  request: a membership is access configuration, and the account itself is the users API's to delete. Each row first
  gets a contentless tombstone in `voc-aggregates` (`AUDIT#tombstone#workspace_members` / `{ws}#{sub}#{job}`:
  the workspace, the run, the legal basis; one per job, so a later erasure never overwrites an earlier record), and the job and its audit row count `member_rows_deidentified`. While the
  account exists, the members list fills an emptied row's email from Cognito, as for a workspace's creator. The
  workspace's audit rows hold subs only (an `account_created` row the email's sha256), so they hold nothing to erase.
  The rows are found by a paged Scan of `voc-workspaces`: the table has no email index, and the email can be on a row
  whose account changed its email or was deleted before 6.11.00, which a look-up of the account by email (Cognito
  `ListUsers`, then the `USER#` rows) would miss. It runs once per erasure job, never on a request path, 100 items a
  page, projecting the key and the email only, within the job's time budget and hand-over cursor; the table holds
  the control plane (workspaces, members, their audit), far smaller than the feedback tables the same job scans.
- History (D2: access rules are primary data): a removal deletes the `MEMBER#` and `USER#` rows and a role change
  overwrites `role`, but each first writes its `AUDIT#WS#{ws}` row with the target, the role before and after, the
  actor and the time, append-only under the audit-row guard: the membership's whole history is kept there.

## Credentials

Decision 19 (since 7.12.00; it replaces decision 8's "one Secrets Manager secret per workspace"): a workspace's
credentials are SSM Parameter Store SecureStrings, standard tier (no monthly fee, at most 4 KB each), encrypted with
the deployment's customer-managed key, one per plugin namespace, so no parameter grows with the number of plugins.
A plugin's config list is not a credential and is not in SSM: it is a row of voc-aggregates.

- **Layout.** The prefix is `/voc/ws` (`/<prefix>-voc/ws` with `-c deploymentPrefix`, the convention of the Radar
  Exa key in [radar.md](radar.md)):

  | Where | Holds |
  |---|---|
  | SSM `/voc/ws/{ws}/credentials/{plugin}` (`lambda/shared/workspace_ids.py`, `lambda/shared/workspace_credentials.py`) | the plugin's keys as one JSON object, bare (`{"api_key": "…", "app_name": "…"}`): every `<plugin>_<key>` the shared secret holds for that plugin but `configs`, its webhook secret (`webhook_secret`) included; at most 4096 bytes (UTF-8) |
  | voc-aggregates `WS#{ws}#PLUGIN_CONFIG` / `{plugin}` (`lambda/shared/plugin_configs.py`, through the workspace layer) | the plugin's `configs` list as stored (its JSON array text): the webscraper's scrapers (`webscraper_configs` in the shared secret), an app plugin's connectors or review pages (`app_reviews_ios_configs`, `app_reviews_android_configs`, `web_reviews_configs`); the deployment's own limits (a scraper 8 KiB, the scrapers 48 KiB in all, any list at most the shared secret's 64 KiB), far under the 400 KB item; `updated_at`, and `updated_by` (the sub of the member who saved it) |
  | voc-aggregates `WS#{ws}#PLUGIN_CONFIG#HISTORY` / `{plugin}#{superseded_at}#{random}` | every list a save replaced: its `configs`, its own `updated_at` and `updated_by`, `superseded_at` and `superseded_by_sub`; kept for good (no `ttl`), exported as `plugin_config_history` |

  Why the lists are rows: no field of any list holds a secret. A scraper holds URLs, selectors, pagination, a
  schedule and labels, and the webscraper builds its own request headers (no header, cookie, token or auth field
  is read from a config); an app connector holds an app id or package name, a display name, a schedule and a Radar
  brand; a review page a public https URL. Every member already reads them whole (`GET /scrapers`,
  `GET /integrations/{source}/apps`). A config that ever needs a credential keeps it under its own key, in the
  plugin's credentials parameter, never in the list.

  The routes still see `<plugin>_<key>` keys (`lambda/shared/workspace_plugin_store.py` maps them), so their merge is
  the one they did on the secret: read, change the plugin's keys, write back; only what changed is written (the
  parameter with `PutParameter`, `Type=SecureString`, the customer-managed key, `Overwrite`, `Tier=Standard`; the
  row in one `TransactWriteItems` with the history row of the list it replaces, the row conditioned on being the one
  the route read (its list and `updated_at`), and before the parameter, so a concurrent save answers 409 and writes nothing of that
  plugin). A value over its limit is refused with a 400
  that says what to shorten, before anything is written.
- **Integrity of the rows.** Any role that may write voc-aggregates could write a config row, so a run trusts no
  row: the web_reviews ingestor re-validates every target on every run (`shared/web_review_targets.py`
  `validated_target`, each page through `checked_url`), and the webscraper fetches every URL through
  `shared/http_utils.py` `fetch_public_url` (the URL policy on each request and each redirect). The app-review
  ingestors take no URL from a row: an app id or package name only reaches the store's own fixed host
  (`apps.apple.com`, `play.google.com`) through its client. Their id format is not re-checked at run time; with
  a fixed host that is a malformed request to the store at worst, not a reach to another host (a gap kept as is).
- **Nothing is made with a workspace.** A parameter or row exists once something is saved in it; one that does not
  exist (`ParameterNotFound`, no item) reads as nothing saved: an empty list or no keys on the routes,
  `WorkspaceCredentialsNotSet` for a run (not counted by the breaker), a webhook delivery refused like a bad
  signature. The 409s a workspace answered while its secret was pending, the pending state and its recovery steps
  are gone.
- **`secret_status`.** The create still writes `secret_status: ready` on `META` and the listing row and answers
  it, but nothing reads it: it no longer reflects a secret, nothing is created asynchronously, nothing gates on
  it, the resolver does not read it, and since 7.12.00 the platform console shows no badge for it. The field
  itself goes later.
- **Readers.** A run in a workspace reads its own plugin's credentials parameter (one GetParameter) and its config
  row (one strongly consistent GetItem), fresh on every run (`plugins/_shared/base_ingestor.py`); a delivery to `/webhooks/{plugin}/{ws}` reads the plugin's credentials
  parameter of the workspace its stored `META` routes it to, kept 60 s per workspace and plugin in the warm container (a missing or
  empty value kept too, a failed read not, at most 256 names: `plugins/_shared/base_webhook.py`); the integrations and
  scrapers APIs read and write the request's resolved workspace's parameter and row of the route's plugin
  (`GET /integrations/status` reads every plugin's: one GetParametersByPath, one Query of the config partition). A
  deployment-wide run, delivery or request still uses the deployment's shared secret (`SECRETS_ARN`), unchanged.
- **IAM** (`voc-datalake/lib/utils/workspace-secrets.ts`), each grant on exactly one workspace id segment (`ws_`
  and 26 `?`, as the DynamoDB `LeadingKeys` conditions use it): an ingestor role may `ssm:GetParameter` only
  `…/credentials/{plugin}` of the plugins it runs (`voc-datalake/lib/stacks/ingestion-roles.ts`), the webhook role
  only `…/credentials/{plugin}` of its webhook plugins (`voc-datalake/lib/stacks/api-stack.ts`), each with a
  `kms:Decrypt` statement conditioned on SSM (`kms:ViaService`) and those names
  (`kms:EncryptionContext:PARAMETER_ARN`), which is no second layer: the same roles hold the key unconditioned
  (below). The integrations and scrapers roles may `ssm:GetParameter` and
  `ssm:PutParameter` on `…/credentials/*` and `ssm:GetParametersByPath` on that path, with `kms:Decrypt` and
  `kms:Encrypt` through SSM for those names; no delete. A standard SecureString is encrypted by SSM calling KMS
  directly, so no `kms:GenerateDataKey` is granted. The config rows need no new grant: every ingestor role already
  reads voc-aggregates and writes its run rows there, and the integrations and scrapers roles already read it and
  PutItem their run rows (table-wide grants that cover `WS#{ws}#PLUGIN_CONFIG` and `#PLUGIN_CONFIG#HISTORY`, a
  conditioned Put inside a transaction included; narrowing them is a separate change).
  Where IAM separates plugins and where it does not: a plugin with a role of its own (a schedule, Bedrock, the
  browser, job notices) reads only its own credentials parameter; the plugins that share `IngestionLambdaRole`
  may each read the others' (the shared role names all their parameters), so between them, as in the shared
  secret, the name the code builds from the plugin's own identity is the boundary. IAM never separates workspaces
  (any one id): only the code, which builds each name from the verified scope, the resolved membership or the
  routed `META`, keeps a run, a request or a delivery to its own workspace (decision 1's soft isolation). The
  workspaces API holds no Secrets Manager or SSM grant at all. These roles also hold the deployment key
  unconditioned for their other resources (queues, tables, the shared secret), so the SSM-only key statements
  state the parameters' reach rather than narrow it.
- **Service limits** (per account and region, shared by every deployment there, prefixed copies included, and by
  anything else that uses Parameter Store; [deployment.md](deployment.md#ssm-parameter-store-limits-a-workspaces-credentials)):
  GetParameter's default throughput is about 40 transactions a second (a quota that can be raised: the paid
  higher-throughput setting); a run makes one GetParameter, a webhook delivery at most one per workspace and plugin
  every 60 s in a warm container. A run's SSM client retries a throttle adaptively, up to 10 attempts
  (`lambda/shared/aws.py` `get_ssm_run_client`); the APIs' and the webhooks' (`get_ssm_client`) make 2 attempts
  (standard mode) with 2 s connect and 4 s read timeouts, so the route with the most SSM calls,
  `PUT /integrations/{source}/credentials` (a read then a write), takes at most 2 × (2 × 6 s + 1 s of backoff) = 26 s
  and answers within API Gateway's 29 s. At most 10,000 standard parameters: one per plugin with saved
  credentials in each workspace, across every deployment in the account and region.
- **Cost**: none per workspace. Standard-tier
  parameters are free at the standard throughput (the higher-throughput setting, if raised, bills per call). The fixed-cost guard
  (`voc-datalake/lib/fixed-cost-guard.test.ts`, `runtimeFixedCostFindings` in
  `voc-datalake/lib/test-support/fixed-cost-rules.ts`) now refuses every grant of `secretsmanager:CreateSecret` or
  `kms:CreateKey` in the app. The workspace delete job (phase 4) will delete a workspace's parameters by path and
  its config rows with its partitions.

## Cost per workspace

- Every Bedrock call logs `workspace_id`, the model and its input and output tokens (`shared/converse.py` and the
  stream Lambda's model client already centralise those calls). A daily rollup writes `WS#{ws}#COST` rows by date,
  and the platform console shows cost per workspace per day and month (tokens × list price, labelled an estimate).

## Export and delete

The owner accepted the proposal below (decision 17, [settled](#tenet-questions-settled-owner-2026-11-12)): the
controller's own request, with its stated basis and a tombstone per deleted item (TENETS.md, D5). Phase 4 builds it.

1. A workspace admin or a platform admin asks to delete the workspace; the web app offers **Export first** (on by
   default).
2. The export job writes JSONL per entity (feedback, projects and documents, personas, memory, agents and workflows,
   conversations, settings) plus the raw objects into one zip under `ws/{ws}/exports/`, with a `manifest.json` that
   says what it holds and what it leaves out (a workspace's credentials are never exported). When it ends, the
   person who started it gets a job notice (when the job could write its outcome: one the timeout killed shows as
   failed an hour later); the export page then offers a download for 7 days (each link, asked for with
   `POST …/export/link` and audited, works 15 minutes; no email is sent). Export objects expire by object tag (10
   days), and an erasure that reaches the workspace deletes them at once (a derived copy, D5). The zip lives under
   the workspace's own prefix, so it goes with the workspace: download it before deleting.
   Since phase 4a (7.17.00, above) the job exports the feedback and the workspace's configuration, history and
   control-plane rows; what is not per workspace yet is listed in the manifest.
   Since 7.20.00 it also exports
   every current object under `ws/{ws}/` except its exports (`raw/`, `silver/`, and any other folder) as
   `objects/<key without ws/{ws}/>`, each its current version when the export's listing reached it (older versions
   are not exported); an object over 3 GiB, too slow to copy in one invocation, deleted meanwhile, or whose key
   cannot be a file name in a zip, is listed in the manifest as not included, with the reason. Already-compressed
   objects are STORED entries with a data descriptor, which some streaming readers reject (central-directory readers
   are fine), and keys that differ only in case or Unicode normalisation can overwrite each other when extracted on
   macOS or Windows (on Windows also keys that differ only by trailing dots or spaces). Since 7.22.00 it also
   exports the workspace's company memory: its company memories, their events and the import rows, each only the
   fields its allowlist names, without any person's hash (a company memory's `conflicts_with` can still hold a
   personal memory's id, and an event's `detail` is exported whole); personal memories and the extraction cursors
   are their owners' only, so they are counted in the manifest, never exported.
   Open: the members' conversations, per workspace since 7.15.00, are not exported yet (the manifest lists them
   under `not_exported`). Their owners are listed since 7.19.00
   (`WS#{ws}#CONVERSANTS`, above), so the export and the delete (step 4) can reach every member's partition, a
   former member's too, by Query on the workspace's own partitions.
   Open (TENETS.md D5, older than workspaces): an erasure by email reaches neither the memory items nor the
   assistant conversations, the deployment's or a workspace's. The erasure job matches an email, and these rows are
   keyed by the person's Cognito `sub`, not their email: a conversation by its owner's, a personal memory by its
   owner's (a company memory by no one's); what either says may name anyone, and the job does not search it.
   Reaching them would take the person's `sub` in the erasure (looked up in the directory while the account exists,
   or recorded with the request), or their email on those rows, so the job could find the person's conversations
   (at `USER#{sub}`, and through each workspace's list of conversation owners) and personal memories; and a rule for
   a memory or a message that names the person in its text.
3. The admin confirms by typing the slug. The workspace's status becomes `deleting`: every request is refused and its
   schedules stop.
4. The delete job (self re-invoking and checkpointed, like `voc-retention`) deletes every `WS#{ws}#` partition of
   every table, every `ws/{ws}/` object with all its versions, its credentials parameters (by path), its MCP tokens, memberships, slug,
   its enabled plugins (the `PLUGIN#{plugin}` / `WS#{ws}` rows of `voc-workspaces`: keyed by the plugin, so a sweep
   of the `WS#{ws}#` partitions does not reach them) and the share grants it gave or used. Copies other workspaces already imported stay theirs (TENETS.md, D8,
   settled above). One audit row stays in a platform partition (name, who, when, counts), with no customer data.
5. With `protectData` the tables stay protected; this is item-level deletion, so it still works.

## Tenet questions, settled (owner, 2026-11-12)

The two points D5 left open are decided, and TENETS.md says so (since 7.05.00):

- **Workspace delete (phase 4): accepted as proposed.** The delete is the data controller's own request under its
  agreement with the deployment, a retention limit the deployment is bound to: it states its basis, is approved by
  typing the workspace's slug, writes an audit row, leaves a tombstone per deleted item like `voc-retention`'s, and
  offers the export first (TENETS.md, D5).
- **Imports and erasure (phase 5): no, an erasure in A does not reach B's copies.** A new data lake tenet, D8: each
  workspace is its own boundary. Sharing data with another workspace copies it there; from then on the copy belongs
  to the workspace that imported it, and nothing done in the source (an edit, an erasure, deleting the source
  workspace) reaches it. Each workspace's admins answer for the data it holds. The share step says so before
  anything is copied: "it will be copied to <workspace>, which then owns its copy". `imported_from` stays as lineage
  (D4), not as a path for the source's changes.

## Workspace import plugin (later)

Workspaces stay fully separate; sharing is an import, like any other source.

- **Approval**: A's admin approves B for one of A's sources (`WS#{A}` / `SHARE#{source}#{B}`, audited). B's admin then
  adds a `workspace_import` connector pointing at it.
- **Modes**, per connector: `raw` copies A's raw objects into B's raw prefix and runs them through B's own pipeline
  (B's categories, models and settings; B pays the enrichment); `categorised` copies A's processed items as they are
  into B's partition, and nothing is re-run.
- **Fetch**: a pull with a watermark per connector over A's date index for that source, plus a backfill window on the
  first run. This plugin is the one sanctioned reader of another workspace's data, through a dedicated repository
  call that re-checks the approval on every run.
- **After the copy the data is B's**: stored as B's own items (`source = ws_<A-slug>_<source>`,
  `imported_from: {ws, source, id}`) and raw objects. Revoking the approval only stops future imports. A's edits,
  erasures, retention deletes and workspace deletion do not reach B's copies (TENETS.md, D8, decided by the owner:
  [settled](#tenet-questions-settled-owner-2026-11-12)); B's admins answer for what B holds, and the share step A's
  admin sees says "it will be copied to <workspace>, which then owns its copy". Copied items are read-only in B (no category or dimension edits); B can delete them and
  disconnect the connector.
