workspace's own profile allows PII, now writes one raw copy per item under `ws/{ws}/raw/manual_import/…`. Retention
deletes each copy with its item. Before the fix the upload wrote one whole file (`ws/{ws}/raw/csv_upload/…`) that
retention never deletes.

## Reasons

The test drives the real manual-import handler (`manual_import_handler`, `POST /scrapers/manual/csv-upload` through
`workspace_route_call`) as workspace A's admin, with real workspace membership resolution. The real `upload_profile`
reads both profile rows from the moto aggregates table, with no stand-in. The faked edges are only the store
(DynamoDB, S3 in moto) and the queue (SQS as a MagicMock that records the messages sent). The test asserts what lands
in the bucket and on the queue: two messages, two distinct raw URIs, exactly those two objects in S3, all under
`ws/{ws}/raw/manual_import/`. That is the per-item archive the item promises, and the opposite of the bug's single
whole file. The expected values (two items, the workspace's root) come from the fixture's CSV and constants. With the
merge removed, the test failed at its own assertion (`_per_item`, line 133, reached from line 143). The failure shows
the bug itself: both messages point at one `ws/…/raw/csv_upload/….csv` file. Restored, it passed 3 of 3. The sibling
tests in the file (the deployment's own uploads, and an unwindowed source keeping its whole file) guard the other
direction, so the merge cannot be applied blindly either.
