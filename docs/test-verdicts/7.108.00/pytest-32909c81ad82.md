## Item

In a workspace, the manual import's profile reader (`shared/ingest_archive.py` `upload_profile`) now merges the
deployment's retention window for the source into the workspace's own profile (`with_deployment_window`). So when a
source has a deployment window and the workspace's profile allows PII, the upload keeps one raw copy per item, which
retention deletes with the item. Before the fix it kept one whole file that retention never deletes.

## Reasons

The test calls the real `upload_profile` on a moto DynamoDB table that holds the deployment's `SETTINGS#sources` row
and the workspace's own sources row. Only the store is faked: the table is moto, and `get_dynamodb_resource` and the
env var are patched for the strict reader's fixture. The test checks three things about the profile it gets back: it
is the workspace's own (label "Trail reviews", pii allow), it carries the deployment's window (90, "Contract clause
4"), and `archive_mode` makes it `item`. The last point is the data-protection outcome the item promises. The expected
values are fixture constants (`WINDOW`, the workspace's label), never computed by the code under test. With the merge
removed, the test failed at its own assertion (line 88), on exactly the missing window, `(None, None)`. Restored, it
passed 3 of 3. It is a plain module-level function, with no skip mark or parametrize, and the brief resolves it.
